# 传输动效：跟随运动，再回到能读懂的空间

先确定当前镜头要让观众看清什么。搬运过程需要速度和方向，解释发送窗口则需要稳定的范围及边界。两个问题适合不同候选，不必把模糊、变焦和滑动同时加上。

参考观察见 [传输深度研究](../studies/transmission-deep.md)，技术依据和实现边界见 [动态模糊技术核对](../studies/motion-blur-technical.md)。原片具体引擎和模糊算法未确认。原创代码在 [transmission-effects.js](../lab/modules/transmission-effects.js)，用 [传输效果工作台](../lab/transmission-effects.html)比较候选；参数和返回状态见 [接口说明](../examples/transmission-effects/API.md)。

## 按问题选候选

| 当前问题 | 选择 | 先看什么 |
|---|---|---|
| 东西移动很快，却像逐帧跳位置 | 跟随曝光对照 | 固定轨迹与当前时刻，只比较曝光关闭和开启 |
| 开了模糊，主体也糊得看不清 | 跟随曝光对照 | 切换固定与跟随视角，观察主体相对屏幕的移动 |
| 跟随时看不出速度 | 跟随曝光对照 | 保留背景参照；让背景朝相反方向移动，勿只对主体加糊 |
| 数据、确认信号和窗口像三个无关动画 | 窗口接力 | 用同一事件和位置关系驱动包、确认及窗口边界 |
| 局部放大之后忘了自己在哪 | 窗口接力 | 保留两端或尺的一部分，同一个窗口框进入特写 |
| 数字还没读完镜头就走了 | 窗口接力 | 抵达后保持结果；下一次运动由新的解释任务触发 |

它们学习的是相对运动与表示交接，不是复制原作者素材。候选中的包数、动作时长和配色为原创演示选择；需要表示TCP机制时，另接可核对的事件数据和协议条件。

代码候选分别为 `look-tracking-exposure`（18秒，建议从9.575秒比较）和 `visualization-window-relay`（20秒，建议从9.55秒观察）。两者保持末态，不自动循环。强度旋钮关闭，避免用装饰性参数改变可核对的事件关系。

## 跟随曝光对照：先让运动关系成立

先关闭模糊，检查主体从哪来、到哪去，以及相机是否真正跟随。随后开启有限曝光，让同一帧内多个时间状态合成。若固定相机看到主体拖长，跟随相机看到主体相对稳定、背景扫过，说明速度感来自正确的关系；若两种视角都只糊主体，应先检查投影与相机采样。

曝光长度由快门角与帧率决定：`T = angle / (360 × fps)`。30fps、180°约16.67ms；在曝光期间屏幕线速近似恒定为600px/s时，轨迹长度约10px。这个例子帮助判断数量级，不是所有物体的统一拖尾长度。

用少量参数形成有区别的候选即可：

| 要改变的感受 | 调整方向 | 检查代价 |
|---|---|---|
| 快速动作更利落 | 缩短曝光 | 逐帧跳动可能更明显 |
| 快速横移更连续 | 适度延长曝光 | 主体细节可能损失 |
| 背景更有掠过感 | 增加有效视差或跟随范围 | 不要改变对象实际到达时间 |
| 模糊出现断续轮廓 | 增加时间样本 | 渲染成本上升；先排除错误状态复用 |

相机有旋转、滚转或透视变化时，每个子样本都重新求相机和对象状态。只把同一截图横向复制，最多是方向拖影示意。不要据此声称三维曝光、光追或真实摄影机仿真。

字幕与读数在曝光后绘制。运动过程中保留必要的短标签，较复杂的结论等镜头回稳后出现。物体上的文字若特意保持锐利，要按追踪标注设计，避免看起来脱离模型。

当前模块用 `cameraMode: fixed | follow` 切换机位，用 `blurMode: none | temporal | spatial` 比较单时刻、时间曝光和空间高斯。`spatial` 根据相对屏幕速度匹配模糊量级，仍然没有计算新的运动位置。默认30fps、180°、16个样本；`fps` 可选30或60，`shutterAngle` 为0–360，`samples` 为4–64。模块在片首尾将中心曝光区间裁到0–18秒，再在剩余区间均匀采样并归一化；这是缩短边缘曝光，并非端点重复或范围外真实状态。

## 窗口接力：框的位置就是正在解释的范围

先在总览中建立发送端、接收端与数据带。窗口框随后进入并停住，让观众先认清它限定了什么。再沿同一个框推近，尺度尺与已确认边界继续可追踪。

一次事件只提交一个新的事实。确认到达后改变已确认位置，再移动窗口；标签在变化之后解释结果。未发生事件时，允许画面停留，或只做轻微的观察镜头。不让窗口每帧弹动来代替机制演示。

如果需要快速交接，可沿包运动方向跟随一小段，随后回到两端总览。快速运动退出后再读总量或比较差异。这里的“停留”可以是对象状态稳定、相机缓慢观察，不一定冻结整幅画面。

代码应将数据坐标和屏幕坐标分开。窗口的位置来自有效范围，局部放大只改变投影，不改变字节尺度或确认状态。样例中的表现事件只是图形演示；不能把固定间隔动画直接称为真实TCP网络求解。

当前样例用6个100B数据包，最多允许3包尚未确认。接收与确认返回是两个不同事件，发送端只在后者到达后提交确认数；窗口外框随后用0.55秒滑移。17.1–20秒保留最终总览。它没有实现完整TCP协议，不应将预设事件时间引用为网络测量结果。

## 迁入正式视频前的四个决定

**先定时间。** 选择中心曝光或结束于当前帧的曝光，在整个段落中保持一致。中心曝光含有当前帧之后的状态，接近声音触发和落定时应检查是否提前。需要精确事件演示时，保留事件时刻和显示时刻两条记录。

**再定颜色和遮挡。** Canvas工作台适合比较轨迹、快门和信息层级；显示编码颜色平均是预览近似。生产线性光曝光应在统一线性工作空间累加，之后做显示变换。每个子样本先解决前后关系，透明图层用预乘颜色与透明度共同累积；不要将各对象的拖尾随意覆盖到前景上。

**按画面选样本。** 先比较同一帧的8、16和32样本，重点看细线与高速转动。静止HUD只画一次，缓冲可以复用，但场景状态必须按子时刻重求。样本多不等于曝光长，也不保证颜色和遮挡正确。

**说明边界。** 首尾可渲染短曝光余量后裁切，或明确使用端点保持。循环状态不连续时不能把末尾取样绕回开头。跨硬切的时间采样应阻断，避免无关场景混在同一帧里。

## 用同一画面对照验收

1. 关闭模糊检查轨迹和事件因果，再保持时间及机位不变开启曝光。不要同时换配色来掩盖变化。
2. 固定与跟随相机分别看一次：主体相对屏幕的运动、背景方向及近远视差都应符合投影。
3. 查看动作开始、最高速、遮挡经过和落定后的帧；文字应保持可读，模型不应因混合暴露本来被挡住的部位。
4. 打乱取帧顺序并重复相同时间，结果应一致；这能发现依赖上次播放的历史拖影。
5. 原速完整播放进入—运输—落定—阅读—退出，再检查首尾。浏览器运行日志只证明运行，不自动代表连续主观审看通过。
