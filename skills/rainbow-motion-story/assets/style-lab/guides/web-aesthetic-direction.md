# 网页审美：把参考变成能用的设计决定

适用于网站选型、首页重构、作品集与工具工作台：有参考图，却不知道该如何说明、选择和落地时使用。视频中的单镜构图仍用[审美方向](aesthetic-direction.md)；字形、色彩角色与可读性见[文字与色彩](type-color.md)；跨面板动作连续性见[界面编排](ui-continuity.md)。

见构 UI 的[这条参考](https://v.douyin.com/Ue12PXM6bjk/)介绍了两种获取设计输入的方法：把叫不出名字的组件动效转成可复制的 AI 提示词，或取得整套网站设计代码后在本地修改内容。获取这些输入能减少描述和起步成本，但最终仍要判断它们是否适合当前任务。下文是为本方法库整理的**原创实践方法**，不把这些细节全部归因于原片。推荐站源铺、实际检查页面与59张源帧的观察范围见[研究记录](../studies/jiangou-ui.md)。

[打开三方向工作台](../lab/web-aesthetic.html)可用同一份研究档案比较布局，修改真实标题、搜索和收藏，试窄屏并导出设计约定。它使用真实HTML与DOM交互；[API与代码入口](../examples/web-aesthetic/API.md)区分布局、设计变量和状态，不连接现有视频工程。

## 先写任务和证据，再写风格

“高级、炫酷、国际化”不能说明用户为什么需要这个页面。用一小段话交代以下内容，再挑参考：

| 设计输入 | 要回答的问题 | 例子 |
|---|---|---|
| 当前任务 | 谁来这里，最先要完成什么？ | 已有创作者找到最近一次成片，打开预览 |
| 内容证据 | 有什么真实内容能支撑页面？ | 成片封面、标题、更新时间、版本、实际预览入口 |
| 主操作 | 看完这一屏后做什么？ | 打开当前项目；其余操作进入项目后处理 |
| 内容顺序 | 不看哪些信息就无法判断？ | 先辨认作品，再看版本与状态，最后选择操作 |
| 品牌特征 | 什么可见特点值得保留？ | 一种标题排法、独特裁切或有用途的材料感 |
| 约束 | 哪些内容和成本不能靠装饰掩盖？ | 封面缺失、标题很长、移动设备、图片加载成本 |

只有一张精美截图时，记录它能证明的部分：构图、可见文字、图形和颜色。截图不能证明按钮有效、滚动连续、移动端合理，也不能证明其代码能直接使用。对参考做笔记时保留“看见了什么”和“准备怎样改”两栏，避免把自己的推测写成原站功能。

## 从页面骨架选择，而不是先换皮肤

下面三类是原创候选方向，名称用于组织比较，不是统一审美标准，也不意味着每个项目都需要同时制作三套。

| 方向 | 内容骨架 | 适合的任务 | 取舍 |
|---|---|---|---|
| `editorial` 编辑式 | 一个清楚观点或主标题，配核心图像；随后按阅读顺序展开证据、章节和行动 | 科普专题、研究展示、产品故事、需要先理解再行动的页面 | 可以建立作者感与叙述节奏；如果用户来这里反复操作，大标题和长叙事会降低效率 |
| `console` 控制台式 | 当前对象和状态明确，主操作靠近内容；列表、详情、筛选与反馈形成稳定关系 | 项目管理、视频编辑、实验工具、需要持续查看和修改的工作区 | 便于比较与操作；密度高时需要明确分组，不能靠每项一张大卡片无限拉长页面 |
| `gallery` 展廊式 | 作品和材料先被看见，少量元信息帮助识别；进入详情后展开背景与操作 | 作品集、素材选择、视觉案例库、以图像判断为主的内容 | 视觉表达直接；依赖素材质量，标题、状态和行动不能被大图吞掉 |

比较候选时使用同一份真实内容、同一主任务和同一关键操作。变化的是信息组织、图文比例、导航与密度，而不是删除难排的文字来证明某套更好看。不要给三个相同的卡片网格换三种底色，就称为三种设计方向。

先画出“用户进入 → 辨认内容 → 获得判断依据 → 采取行动”的路径。每块区域都应能说明它在路径中的作用。重复强调同一个卖点、没有去处的按钮、首屏之外无法发现的重要操作，都应回到结构层解决。

原片中的 HELIEX 值得学习的是完整阅读路径：首屏之后继续呈现成果、服务、流程和定价，浅深章节交替，重复的等距图形保持网站身份。选参考时沿整页检查“上一节回答了什么、下一节为什么出现”；不能只取一个漂亮首屏，再用无关卡片填满后文。具体源帧与观察时间窗保留在研究记录中。

## 给组件起名字，也写清它的行为

能叫出组件名，便于检索和与 AI 协作；名字本身不是需求。优先使用已有术语，再描述这次的内容与状态。例如：

| 看见的形式 | 可以检索的名称 | 还需说清的内容 |
|---|---|---|
| 两侧图文分工的开场 | split hero／分栏首屏 | 哪侧先读、图像说明什么、小屏先后顺序 |
| 一组只切换同一区域的选项 | tabs／标签页 | 选中项、对应面板、键盘切换、切换时是否保留编辑值 |
| 点开才读细节的一行 | accordion／折叠面板 | 默认展开哪项、能否多开、收起后是否仍能辨认主题 |
| 缩略图变成同一对象的详情 | shared element transition／共享元素过渡 | 对象 ID、起止容器、裁切与焦点交接、返回位置 |
| 鼠标附近局部明暗变化 | spotlight／聚光跟随 | 是否只是装饰、触屏如何呈现、是否影响文字对比 |
| 一组可筛选作品 | filterable gallery／筛选画廊 | 筛选项、数量、无结果提示、清除筛选与返回位置 |

无法确认名称时，直接写动作：触发条件、变化对象、结果、如何退出。例如“点击作品缩略图后，在同一页打开详情；缩略图与大图保持同一作品身份；关闭后回到原滚动位置”。这比猜一个酷炫的组件名更可执行。

需要实现的状态至少应覆盖本次真实流程。筛选就处理无结果；保存就区分提交中、完成与失败；删除前后要能知道对象去了哪里。按钮收到点击时可以先给反馈，成功状态应等实际结果，不拿装饰动画代替完成。

网页使用真实 HTML 语义和交互。视频中的 Canvas 界面适合展示动作，不宜直接充当需要复制文字、键盘操作或读屏的产品页面。复用现有动效时，把资产与事件契约接入真实状态，再决定怎样动。

公开代码也需要复核。源铺此次查看的按钮示例把原生输入设成 `display:none`，会移除这些输入的常规键盘聚焦能力；复制后外形接近，不代表交互已经合格。根据实际用途选择按钮、单选组或标签页语义，验证选中状态、键盘可达与焦点返回，再保留合适的动画参数。原站某个组件的速率不是所有页面的默认值。

## 将风格拆成可调的设计变量

提取参考时，区分结构决定与表面变量。分栏比例和章节顺序属于结构；文字颜色、边距、圆角和动效时长属于变量。先解决前者，再微调后者。

| 变量组 | 建议保留的角色 | 检查方法 |
|---|---|---|
| 色彩 | 页面底、表面、正文、次级文字、主操作、状态 | 在实际背景检查对比；主操作颜色不与告警含义冲突 |
| 文字 | 展示标题、章节标题、正文、辅助信息、数值 | 用真实中文比较层级、换行与阅读宽度；长标题不能只靠无限缩小 |
| 空间 | 内容宽度、页面边距、组间距、组内距 | 距离能说明哪些东西属于一组；大空白也要有阅读或构图用途 |
| 形状 | 容器、按钮、图片裁切、边框、阴影 | 同功能保持可识别，材质区别与组件用途相符 |
| 动作 | 触发反馈、导航、展开、结果、退出 | 按距离与信息量选择速度；结果可读，减少动态效果时仍然可用 |

用角色 token 表达选择，例如 `color.text`、`color.surface`、`space.section`、`type.body`，不要把每个元素都写成无关联的独立参数。token 数量应服务实际组件；无需为尚未出现的功能建立一整套空配置。

参考的美感可能来自照片、排版或内容，而不来自渐变和阴影。提取时写清“移除主图后还有什么成立”。若必须依赖高质量素材，就把素材需求列入设计输入，不能用随意占位图评价整套方案，更不能把别人的人物、标识或作品默认变成自己的资产。

## 小屏调整优先级，不只缩放尺寸

先保留任务所需的信息和主操作，再决定哪些工具折叠、哪些说明进入详情。桌面分栏变成单列时，阅读顺序要按语义重新检查；不能因为 DOM 写在后面，就让关键状态排到长图之后。

控制台式页面尤其要分清“当前对象”和“全局导航”。屏幕变窄后可以把次要检查器放进抽屉，但标题、选中状态、未保存状态与主要操作要继续对应同一对象。展廊式页面需要保留作品标题和进入详情的方式，不让悬停成为唯一入口。

检查页面自然滚动、键盘焦点和弹层关闭后的返回点。降低动态效果时，界面可以直接显示目标布局，但同一操作的结果和可达性应保持。页面没有必要为了“生命力”在空闲时持续漂浮、呼吸或移动正文。

## 用真实中文验证，不用短占位词蒙混过关

至少放进本项目最长标题、正常长度说明、一段较长说明、数字加单位和缺少图片的项目。观察以下情况：

- 标题换成三行后，是否挤掉主操作或遮住图像中的主体。
- 中文、英文缩写与数字混排后，基线、字重和标点是否协调。
- 项目名相似时，能否通过封面、版本和状态辨认，不只靠不同颜色。
- 缩略图暂未加载或没有封面时，页面是否仍可操作，布局是否突然跳动。
- 错误与空状态是否告诉用户下一步能做什么，而不是只放一句“暂无内容”。

可计算检查包括对比度、溢出、重复 ID、可聚焦控件与导出配置的一致性。人工检查包括视线顺序、内容适配、品牌辨识和素材关系。两类结果分开保存；不要将它们拼成一个看似精确的“AI 审美分数”。

## 把选用理由交给下一次制作

保留一份简短设计决定，足以让后续智能体复用，而无需重新猜测：

```json
{
  "task": "找到最近一条成片并进入预览",
  "audience": "已有创作者",
  "primaryAction": "打开项目",
  "contentPriority": ["封面与标题", "版本与状态", "操作"],
  "direction": "gallery",
  "reason": "主要选择依据是画面，缩略图能帮助辨认作品",
  "tradeoff": "复杂编辑工具进入项目后再展开",
  "referenceEvidence": [],
  "tokens": {},
  "layout": {},
  "review": {"visual": [], "interaction": []}
}
```

这是记录结构示例，不与工作台的导出字段逐项相同。当前工作台通过 `buildSelection(state)` 导出真实选择、标题、搜索、收藏、理由、变量和布局，`designPrompt(state)` 生成可读制作约定；实际接口以[API](../examples/web-aesthetic/API.md)为准。CSS导出只有变量，完整布局仍需对应样式与控制器。理由若只有“更高级”，应补出它帮助用户完成哪一步；如果某个参考不适合，也记录舍弃原因。

交给 AI 的制作指令可以按这条顺序写：**任务与真实内容 → 选定骨架与理由 → 组件及其状态 → 颜色、文字和空间角色 → 小屏优先级 → 可观察的验收条件**。允许模型在这些约束内提出不同布局；不要用几十个互相冲突的风格词替代判断。
